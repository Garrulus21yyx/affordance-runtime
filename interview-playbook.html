D1 · 用 30 秒介绍项目，怎样抓住重点？

短答：我做的是 DOM-first 通用 GUI Agent Harness，让低成本工具调用模型具备网页操作能力。核心是把页面、动作结果和状态变化组织成模型能理解的上下文，用 Monitor 发现无进展循环并触发策略重审；执行与平台解耦，独立分支已复用到 AndroidWorld；最后用原生验证器和逐步 Trace 判断到底完成了什么。

机制与证据

三分钟展开顺序：① 世界呈现与长程上下文；② 同一决策循环如何接 Web/Android；③ 一个成功、一个失败案例如何被评测和修复。先说设计解决的问题，再说模块名。

继续追问：如果追问“便宜多少”，说明 DOM-first 是成本策略，整体省钱幅度需要同条件实测；不要用模型单价替代每成功任务成本。

定位：项目 README；本页三条简历入口。

D2 · 你到底自研了什么，哪些复用现成能力？

短答：自研 World 呈现、动态工具合同、语义动作绑定、单循环控制、动作效果反馈与 Monitor；浏览器交互交给 Playwright，环境生命周期和任务评分复用 BrowserGym/native evaluator，模型协议与摘要能力复用 PydanticAI/Harness。

机制与证据

把个人工作展开为一个边界：输入是什么、输出是什么、失败怎样表达、哪次 trace 证明它曾经出错。团队规模、日期和个人贡献应按本人实际补充；框架接入不等于重写底层。

继续追问：如果问“是不是套壳”，用 Task316 的 source → model-input 可发现性缺口，解释为什么仅调用浏览器 API 无法修复。

定位：CoreAgentLoop；World owner

D3 · 为什么 DOM-first？纯截图和固定 Playwright 脚本有什么不同？

短答：DOM/AX 提供文字、层级、角色和可操作状态，适合低成本文本模型；截图补充图像、空间和视觉属性。模型每步依据当前状态选择动作，适用于路径事先未知的任务。

机制与证据

固定流程明确时 Playwright 脚本更直接；Canvas、自绘控件、错误或缺失的可访问性信息会削弱结构路径，此时通过同一观察接口引入视觉证据。DOM-first 不是把结构缺口解释成任务不可能。

继续追问：如何证明路线有效？同一任务、模型和预算下比较结构/结构＋视觉；分别报告结构充分与视觉依赖子集，并计入视觉调用成本。

定位：src/affordance_runtime/world/orchestrator.py；AgentOccam

D4 · 你说五层上下文，具体是哪五层？

短答：页面结构化折叠、动态工具裁剪、单轮联合预算、过期历史清理、轨迹语义摘要。前两层减少进入请求的冗余，第三层负责完整请求容量，后两层处理跨轮增长。

机制与证据

层机制保留的不变量
世界呈现PageMap、区域展开、Record/ControlGroup、coverage/cursor记录字段与组成员关系；不完整必须可见

语义摘要Harness summarizing compaction关键结果与事实；近期调用/结果配对保真

继续追问：这是按职责归纳的五层治理，不是连续调用五次 LLM，也不是五级缓存。

D5 · World 已经有内容，为什么模型仍然找不到？

短答：源数据存在不等于模型可发现。World 需要保留层级和记录边界，PageMap 需要暴露可理解的区域描述，read/search 必须返回同一完整语义单元。

机制与证据

Task316 的 contributor 数据已经保留，但匿名 Collection 难以发现，模型输入未包含目标邮箱。修复为现有集合生成有界公开描述，再由通用 read_region 返回整条记录；没有增加“找邮箱”规则。后续该任务 11 步 native success。

继续追问：如何证明泛化？生成不同字段名、行数、文本和嵌套结构，验证字段归属、顺序及 read/search 一致性，再用未调参任务验证。

定位：src/affordance_runtime/agent/context/world_region_index.py；Task316 记录

D6 · fresh observation、ToolResult、previous_transition 是不是三份重复状态？

短答：fresh World 回答“现在是什么”；同调用 ToolResult 回答“刚才执行和局部效果怎样”；previous_transition 将最新意图—动作—效果与受影响的 fresh 语义单元相邻呈现。它们分工不同，但都消费已提交的事实。

机制与证据

执行后先采集新 World、形成 typed ActionOutcome 和 StepResult，再投影同一 tool_call_id 的结果。最新 transition 不重复塞进较早 recent_trajectory；旧历史保留语义目标而不保留失效操作引用。模型看到的是连续关系，而不是孤立的 success 字符串。

白板上展开一轮

W_t + Goal + Catalog_t → ToolCall(id=c17, activate E4)
→ admission / currentness / private binding
→ ExecutionReceipt → acquire W_t+1 → ActionOutcome
→ commit StepResult
→ ToolReturn(id=c17, dispatch + effect)
→ 下一请求：W_t+1 + previous_transition + 较早轨迹 + Catalog_t+1

上面是教学时序，不是可直接调用的 API。实际 GUI ToolReturn 含 dispatch.completion / receipts 和 effect.availability / observed_change / local_postcondition / evidence_method / reason / evidence_refs。效果不可用时保留 reason，如 sent_unknown 或 not_evaluated，不能填一个假的“没有变化”。

ToolResult 是反馈载体；fresh World 是当前事实。不能在 executor 返回时就先给模型“成功”，等下一次才补上未满足的后置条件。读取类工具也没有 GUI dispatch，需要保留其内容、覆盖范围和新增信息语义。

继续追问：点击 sent 但弹窗没出现，是否成功？只能证明发送；局部效果需要后置证据，任务成功还要 native evaluator。

定位：src/affordance_runtime/agent/tool_result_projection.py；src/affordance_runtime/agent/context/step_projection.py

D7 · 页面变化就代表任务进展吗？

短答：不代表。Runtime 呈现 observed change、local postcondition 和新增信息，ActionPolicy 解释是否推进用户目标，TaskEvaluator 负责任务完成。

机制与证据

后置条件使用 satisfied / unsatisfied / unknown。输入值发生变化但被 UI 正规化时，不能直接判失败；点击已 active toggle 可能撤销已满足状态。GoalPlan 没有 mutable item status，模型每步结合 fresh World 重新判断。

继续追问：没有变化是不是该停？读取已有页面但得到新记录可能有信息增量；反过来不相关页面变化也可能没有任务价值。Monitor 不充当语义进度评委。

定位：src/affordance_runtime/evaluation/action_outcome_projector.py；src/affordance_runtime/model/policy/prompts/grounded_agent.yaml

D8 · 到底什么时候压缩？80%、50%、30%、12% 是什么分母？

短答：先做确定性的历史清理，再检查两个触发条件：完整请求达到有效输入容量的 80%；或历史达到可用历史容量的 50%，且近期保真尾部以外至少有 15% 可回收。目标为历史容量的 30%，近期配对完整尾部预算为历史容量的 12%。

机制与证据

完整请求与可用历史容量不是同一个分母。历史空间是在当前请求中为 World、tools 等留出预算后的容量；15% 可回收门槛提供滞回，避免刚压完又触发。30% 是目标配置，不是实测节省 70%。摘要仍受输出上限约束。

数字推演：只用于解释阈值

假设当前可用历史容量 H=40,000 Token，历史已用 22,000，则超过 50% 水位；近期保真尾部预算为 4,800，可回收前缀需至少 6,000。符合这两个条件才走 history-pressure arm；目标摘要后历史预算为 12,000。若历史用了 21,000，但尾部以外只有 3,000 可回收，就不因历史水位单独启动；完整请求的容量压力仍可独立触发。

H 不是固定的模型 context window：当前页面和工具变多，留给历史的空间可能变小。估算用于准入，provider usage 用于事后测量，两者有误差，因此还保留 protocol reserve 与 safety margin。输出上限和摘要语义也决定实际压缩结果，不能保证恰好落在 30%。

继续追问：阈值怎么选？当前是工程配置；在固定任务集上比较质量、触发频率、调用耗时和总 Token，不能把这些比例包装成理论最优。

定位：阈值常量与触发实现

D9 · 哪些可以删，哪些必须保留？为什么不能直接截最后 N 轮？

短答：删过期页面和历史媒体，保留当前目标、最新 World、近期 typed call/result 以及完成任务需要的精确业务值。旧操作引用按 producer 声明的字段路径清理，不能按 E7 之类的字符串正则误删合法文本。

机制与证据

较老响应中的私有 thinking 只有在结果已闭合且该响应自身存在公开文字结论等条件下才可过期；未闭合交换和保留尾部不能拆。固定 N 轮无法控制每轮长度，也可能丢掉前面取得的最终答案字段。

继续追问：能否用“已选中某按钮”摘要决定下一步？不能，它可能已过期；当前 UI 要重新看 fresh World。

定位：src/affordance_runtime/model/policy/pydantic_ai_bridge.py；src/affordance_runtime/agent/context/contracts.py

D10 · 摘要是什么格式？二次压缩会不会逐渐失真？

短答：摘要按“已完成结果—关键事实—失败策略”组织，当前 prompt 分别限制最多 8、8、2 项，并优先保留最终答案需要的精确值与来源。摘要是历史提示，不是可执行计划或当前状态。

机制与证据

再次压缩会面对前次摘要和后续已闭合交换，因此可能累积语义损耗；不能宣称摘要完全无损。保留原始 Trace，检查精确值和来源是否还在模型可见输入；用重复压缩后的信息保留率和最终 native score 检验，不能靠摘要读起来通顺验收。

继续追问：用户修订目标怎么办？旧 plan 失效，重新编译；当前目标锚点由 TaskGoal 重建，不让旧摘要继续当目标 authority。

定位：摘要 prompt 与 SDK history

D11 · 怎样保证 ToolCall 和 ToolResult 不被压断？摘要失败怎么办？

短答：给 Harness 原始 typed PydanticAI history，让它在合法调用/结果边界选择 cutoff；接受候选前再验证完整消息代数。摘要失败、超时或候选非法时保留输入历史，随后重新做容量准入。

机制与证据

历史故障曾把 ToolReturn 临时改成 SystemPrompt 来显示全文，第三次摘要截断时失去调用配对，provider 因孤立结果拒绝。修复是恢复原始 typed messages；这不是多加一次 provider 重试能解决的问题。

继续追问：保留原历史仍超限？返回 typed capacity failure，不能静默删掉证据；压缩与 action 共用 deadline，压缩耗时也要计入。

定位：src/affordance_runtime/model/policy/pydantic_ai_bridge.py；pair-safe compaction 故障记录

D12 · 怎么测压缩有没有丢信息，而不只是看 Token 下降？

短答：分三层：结构性质验证记录与调用配对；独立标注或生成的精确事实保留测试；同任务的压缩开关配对 benchmark，观察成功、重复动作、总消耗和延迟。

机制与证据

事实保留率 = 压缩后仍可正确取出的必需事实 / 标注必需事实；单列值、来源、用户约束和覆盖范围。包括同名记录、长字段、重复摘要、目标修订和相似操作引用文本。测试答案只进入评分器，不注入产品 prompt。

继续追问：如果 Token 少了但成功率降了？报告 trade-off；优先定位哪类信息丢失，不以节省 Token 单独宣布改进。

定位：Atlas EVAL-015、MEM-033/041；本页评测方案。

D13 · Monitor 究竟能看到什么？是不是再调用一个 LLM 看截图？

短答：它消费已提交 StepResult、前后 public World digest、动作及执行回执、局部效果、任务评估状态和 typed InformationDelta；维护有界 transition/result identities。它不是截图识别器，不读模型内心推理，也不解析任务语义。

机制与证据

输入用途
操作与语义目标/参数的稳定签名跨失效 E-ref 识别同一尝试
前后 public World semantic digest识别环境事实是否变化
dispatch + 局部效果区分发出动作与观察到有效操作结果
NEW_INFORMATION / 已见结果摘要区分读取新信息与反复读取
native task outcome任务已终止时关闭监测生命周期

继续追问：findings digest 等诊断变化不是任意清空 failure center 的许可，关闭必须符合 owner-produced escape 条件。

定位：EpisodeMonitor.evaluate

D14 · 如何发现震荡？为什么不是连续三次点同一个按钮？

短答：检测操作—结果转移的重复及短混合循环，同时用未解决 failure center 保留已进入的无进展成员，覆盖 S→A→S→B→S 这种非固定周期的绕圈。

机制与证据

单看 action name 会把合法重复输入误判；单看前后两个步骤会漏掉夹杂搜索/读取的重复。签名基于语义尝试和结果 World，而非临时句柄。center 有界，当前最多 16 个不同转移/结果；容量耗尽也返回 control_stalled。

继续追问：16 是什么？存储/执行边界，不是“允许点 16 次”的启发式成功标准；普通任务总步数预算另有 owner。

定位：src/affordance_runtime/agent/monitor.py

D15 · 怎么让 Agent 及时换策略？Monitor 会替它选择新按钮吗？

短答：第一次确证循环时，将停滞事实与硬约束注入恰好下一次 ActionPolicy 决策；同一策略角色进入 deliberate 配置，获得配置中的推理/模型/输出预算增强。替代路线仍由模型根据 fresh World 和当前工具选择。

机制与证据

反馈可以促使模型重新检查阻碍、获取缺失证据、换路或提交已有支持的结果。当前没有独立 Reflector，也没有要求工具附带 recovery_basis 标签；标签无法证明真正重审。再进入已记录的无进展成员时 Runtime 终止循环。

继续追问：这能保证模型想出新策略吗？不能。Monitor 保证一次可见的调整机会与有界控制；策略恢复成功率要独立评测。

定位：src/affordance_runtime/agent/decision_capability.py；src/affordance_runtime/model/policy/prompts/grounded_agent.yaml

D16 · 换成 read/search 后，为什么还不能重置停滞？

短答：换操作本身不是逃离停滞。若没有 owner 产生的新信息、语义 World 变化或有效 GUI 结果，尝试加入原 failure center；signal 被消费仅表示模型看过反馈，不代表问题已解决。

机制与证据

Task798 曾夹杂读取与搜索，使旧实现不断创建 attempt=1 的恢复信号，跑满时间。现在 failure-center identity 跨这些尝试保留；后续 witness 在第 18 步 control_stalled，但模型仍未给出任务所需的 typed negative。

用状态转移解释生命周期

尚无 center：记录 transition/result
首次重复：建立 center，发一次 recovery signal
下一 ActionPolicy：消费 signal，进行一次策略重审
其后无进展的新尝试：加入同一 center
其后重入 center 成员 / center 容量耗尽：control_stalled
有 owner-produced escape：清空 center，恢复普通推进

signal 的可见寿命是一轮，center 的私有寿命直到逃离或终止；把两者合成“recovery 已消费，所以恢复结束”正是以前的生命周期缺口。暂停时 checkpoint 保存 typed Monitor snapshot，恢复后只有 fresh World semantic digest 匹配才重装对应 center，防止把旧页面的循环约束套到新页面。

继续追问：这个结果算成功吗？是有界控制证据，不是任务成功；不能用“少跑了几分钟”替代 native score。

定位：src/affordance_runtime/agent/monitor.py；Task798 witness

D17 · 如何避免误杀有进展的重复动作？动态页面会不会绕过检测？

短答：有 fresh semantic World 变化、NEW_INFORMATION 或可验证的操作进展时解除相应 failure center；合法重复操作不应只因名字相同被拦截。

机制与证据

逐次删除字符虽低效，却真实改变字段，属于策略效率问题。相反不相关动态内容若进入 semantic digest，可能掩盖停滞；因此摘要字段选择与新信息定义需要性质测试和真实页面验证。机械不变量不等于语义最优。

继续追问：测试建议：参数/字段顺序变化、动态噪声、重复但有效输入、空读、新记录、hub-and-spoke、暂停恢复；明确误报和漏报定义。

定位：src/affordance_runtime/agent/monitor.py；failure-center 当前合同

D18 · Monitor 如何评测？停得早会不会只是把失败变多？

短答：机械性质验证“重复有界、真实变化可逃离”；live 则联合报告循环率、恢复后成功率、停滞后的额外步数与失败消耗。必须检查提前中断原本可成功任务的代价。

机制与证据

继续追问：归因：检测没触发、反馈未进入物理请求、模型看见却仍绕圈、Runtime 没按约束终止，是四种不同缺口。

定位：Atlas AGT-119、EVAL-009；配对实验建议，不声称已完成该消融。

D23 · 指标的分母是什么？怎样避免只统计成功任务？

短答：同时报告成功、失败、未知与 measurement coverage。预算内验证成功率使用已启动任务为分母，未知显式列出；token/time 缺失不是零。每成功任务摊销消耗包含成功和失败运行的全部已测成本。

机制与证据

设 N 为启动次数，S 为 verified success：成功率 S/N；若成本完整且 S>0，摊销成本 = Σ全部运行成本/S。输入、输出、cache、compiler、repair、vision、compaction 应说明覆盖范围；当前部分历史只含 policy tokens，不能称全角色总成本或美元成本。

算一组小样本，识别缺失与零

教学样本共 4 次：A 成功耗 10k，B 失败耗 20k，C 成功耗 15k，D 结局未知且 Token 未测。验证成功率为 2/4=50%，同时列 unknown=1；已测 Token 小计 45k、覆盖 3/4。不能报“总 Token 45k”或“每成功任务 22.5k”，因为 D 的消耗未知。若补齐 D=5k，完整总量才为 50k，摊销值为 25k/成功任务。

输入 Token 的下降与费用下降也不等价：不同模型、缓存命中、输出、升级调用和视觉计价可能不同。没有完整定价配置时只报告已测量维度，不用 Token 乘一个随手估计的单价。

继续追问：失败耗时高怎么办？保留；只看成功任务平均延迟会产生幸存者偏差。若未知结局存在，可额外给 S/N 到 (S+U)/N 的描述性边界。

定位：Labs measurement scope；本页为指标讲述口径。

D28 · Badcase 怎么归因？不是让另一个 LLM 写一句“推理失败”吗？

短答：沿 source → World → delivery → 物理模型输入 → policy call → binding → dispatch → fresh World → evaluator 找首次偏离合同的边界。Trace 提供证据，归因结论是派生分析。

机制与证据

证据对比优先检查
源里有，World 没有Surface projection / 来源完整性
World 有，模型输入没有可发现性、折叠、预算、交付覆盖
输入正确，动作不对ActionPolicy/模型语义；需多样本验证
语义调用合法，绑定/执行不对Binder、currentness、executor
dispatch 成功，预期效果没有页面后置条件、异步时序、未知结果
原始结果存在，报表缺失或全零finalization / metric projection / reporting

现场下钻操作

  1. 在结果表锁定 attempt/case/seed，打开正式 verdict 与 measurement validity。
  2. 找到首次异常前后的 step，检查 before/after World 和执行回执。
  3. 若怀疑模型没看见，直接检查该次物理 input_messages 与 ToolCatalog；不能只看准备阶段的 Context 对象。
  4. 若源数据有、物理输入无，向上对比 source topology、区域目录、coverage、预算和交付；若物理输入完整，则保留模型原始输出及 repair。
  5. 写出可证伪假设：修复哪个转换后，同一类型输入应满足哪个性质；最后看 held-out 是否仍需新生产分支。

这条链用 attempt/case、step、tool_call_id、World revision、provider request/repair 身份关联。Trace、分析 JSON 和可视化都只消费事实；不能在分析器里重建一个“正确结果”再拿它当 native verdict。

继续追问：“最后一个报错”可能只是下游症状。先建立反例和 owner，再决定改 prompt、投影或执行边界。

定位：Atlas EVAL-009/016；src/affordance_runtime/agent/tool_result_projection.py

PydanticAI：选型、用法与替换成本

这部分按当前代码和官方文档比较。仓库未证明做过所有候选的历史 PoC，因此不把今天的比较伪装成过去的实验。

D32 · 为什么选 PydanticAI？不要只回答“类型安全”。

短答：这个项目需要模型提出当前工具调用后立即把控制权交回 Runtime；需要保留 provider 的 typed message、call_id、thinking 和多模态部分；还要在同一消息模型上做压缩、重试与持久化。PydanticAI 的 ExternalToolset / DeferredToolRequests 与这些边界相合，而 Python/Pydantic 已是项目合同基础。

机制与证据

代码不是把浏览器 click 注册成可自由执行的 SDK 函数。先从 World 编译 ToolCatalog，再把 ToolDefinition 放进 ExternalToolset；Agent 返回 DeferredToolRequests，bridge 解析唯一合法动作，Runtime 做风险、绑定和时效检查后才执行。这样复用协议层能力而保留外部副作用的控制。

另一个实用收益是 SDK 的 ModelRequest/ModelResponse 及 ToolCallPart/ToolReturnPart 可以直接用于历史序列化和 Harness 摘要，不必在多个自定义 JSON 聊天格式之间往返。代价是 bridge 与 SDK 消息语义和版本存在耦合，升级需要兼容测试。

继续追问：为什么不是类型校验越多越好？JSON Schema 只能验证表示，不能证明目标当前存在、点击真的生效、用户允许操作或任务完成；这些仍由 Runtime 的领域合同处理。

定位：src/affordance_runtime/model/policy/pydantic_ai_bridge.py；官方 Deferred Tools。

D33 · 沿一次真实调用说出 PydanticAI API 和对象怎么流转。

短答：CanonicalProviderEnvelope 被 codec 转成 instructions、prompt、ExternalToolset、message_history 和 DeferredToolResults；Agent.run 返回本轮消息与 DeferredToolRequests，bridge 再向 Runtime 返回一个语义动作。

机制与证据

  1. TurnPacker 完成 World、tools、history 和容量准入，固定本次 envelope。
  2. 建立 Agent(..., output_type=[str, DeferredToolRequests], retries={tools: ..., output: ...})。允许 str 进入解析分支，是为了由 output_validator 明确拒绝纯文本并产生 ModelRetry，不表示运行时接受纯文本动作。
  3. run(..., toolsets=[ExternalToolset], message_history=..., deferred_tool_results=..., usage_limits=UsageLimits(request_limit=...)) 发出请求；物理设置来自当前 profile。
  4. capture_run_messages 在每次 SDK run 的 finally 中捕获消息，即使后续验证抛错也留下交换；provider 初始与 repair 调用记录各自输入/输出。
  5. 解析 DeferredToolRequests 并验证唯一合法当前 tool call，映射到 SelectAction 或本地工具；Binder/Executor 位于 SDK 调用之后。
  6. 提交 StepResult 后，以同一 call_id 回填 ToolReturn/DeferredToolResults，下一轮附带最新 World 继续。

继续追问：如果回答“SDK 自动把所有工具执行完”，说明没有理解这个项目的集成方式。当前 provider-free 验证要检查“未通过 runtime admission 的提案，dispatch 次数为零”。

定位：run_policy_envelope / _pydantic_model_boundary_codec

D34 · 用了 PydanticAI Agent，为什么还保留 CoreAgentLoop？是不是双循环？

短答：PydanticAI 内部可以因协议和输出校验发生有限交换；CoreAgentLoop 拥有跨 GUI 步骤的运行状态。两者范围不同：前者取得一份合法提案，后者执行一次外部动作、观察效果并决定继续或终止。

机制与证据

模型一步可能经历输出 repair，但不能因 repair 多点击一次。当前工具目录绑定 fresh World，proposal 通过后才解析私有参数。Runtime 在 step 边界处理用户暂停/取消、风险确认、currentness、post-acquisition、Monitor 与 evaluator。SDK 的 run 结束不代表 GUI task done。

如果换成让 SDK 的内置 tool loop 直接调浏览器，再由外层重复执行同一动作，就会有双重执行权；因此 ExternalToolset 的外部执行交接是关键。SDK 托管的 step persistence 也不取代 Runtime checkpoint 中的控制与环境事实。

继续追问：模型一次返回两个 ToolCall 怎么办？即使 provider 忽略 parallel_tool_calls=false，边界也必须验证恰好一个；不截取第一个悄悄执行。

定位：src/affordance_runtime/agent/core_loop.py；src/affordance_runtime/model/policy/pydantic_ai_bridge.py

D35 · 和原生 SDK、LangChain、LangGraph、smolagents 怎么比较？

短答：比较的是本项目需要的控制边界，不是给框架排总榜。原生 SDK 更直接但消息恢复要自己维护；LangChain 有现成 agent 与 middleware；LangGraph 擅长显式持久图编排；smolagents 的代码行动路线适合另一类执行边界。

机制与证据

候选合理使用场景本项目的具体取舍
原生 provider SDK / HTTP单 provider、协议简单，要求最大 wire 控制需要自行维护消息配对、重试、工具描述、摘要与序列化；早期原型可行，多角色/协议演进维护面增大
LangChain create_agent希望快速构建 agent loop，使用 middleware 和集成生态也有类型化输出与工具控制，并非“不类型安全”；本项目已有领域 loop，选择更贴近现有 typed history 的模型边界
LangGraph长生命周期图、分支、持久化恢复、HITL 编排可以实现同样系统，但必须明确定义图 state 与 World/Runtime checkpoint 的唯一归属；目前没有证据要求再迁移这层
smolagents简洁的 agent，尤其代码动作与 sandbox 场景代码执行灵活，但任意脚本容易跨过本项目“单次语义动作→绑定→效果”边界；若采用其工具调用模式仍需相同领域适配
PydanticAI + Harnesstyped Python 消息、外部工具交接和历史压缩当前边界契合；承担版本、provider 差异与 wrapper 正确性的测试成本

继续追问：“你都实测过吗？”当前没有覆盖所有候选的公平 PoC 证据。这是可核对的能力比较；如果要重选，应拿同一工具交接/中断/异常历史任务做原型。

定位：官方文档于 2026-09-07 核对；本项目选择理由由现有集成代码支持。

D36 · PydanticAI 的 retry、你的 repair、网络 retry 会不会指数放大？

短答：必须按层共享预算。schema/output repair 改正提案表示，transport retry 处理请求传输；两者都不能回放已执行 GUI 副作用。当前同一语义 envelope 共享 transport allowance，并设置 SDK request_limit 与整体 policy deadline。

机制与证据

普通输出校验和 deliberate 完整重试有不同预算：deliberate 不叠加内部多轮修复，最多一次同上下文完整输出重试；representation repair 不再开嵌套输出重试。每次物理 SDK run 用独立 capture context 记录，因为 capture_run_messages 只捕获该 context 的第一场 run。

压缩先花掉的时间也要从剩余 action timeout 中扣除，不能静态分出永远不可借用的额度。已送达但效果未知的 GUI 请求不在 provider retry 的语义范围内，要进入新的观察/协调路径。

继续追问：验证：注入超时、纯文本、截断、多调用、缺字段，断言物理请求次数有界、每次 transcript 存在、未执行提案零 dispatch、已执行动作不因格式失败重放。

定位：协议请求预算与 deadline 传播

D37 · 用了框架还遇到什么坑？怎样判断是 SDK 的锅还是 wrapper 的锅？

短答：已知配对压缩故障属于 wrapper：为了让摘要看到长 ToolReturn，把它伪装成 SystemPrompt，破坏了库依赖的 typed boundary。SDK 不能再识别 call/result，所以第三次增量摘要出现孤立结果。

机制与证据

排查顺序是比较原始 SDK messages、临时摘要视图、返回候选及最终 provider envelope。在 SDK 原始历史上复现，若错误消失，则先修 wrapper 的合同。最终去掉伪装，让官方 typed history 通过；候选整体合法性校验失败时恢复原历史。

依赖选择不是“一劳永逸”。当前 pyproject 将 pydantic-ai-slim 限制在 2.33 系列、Harness 限制在 0.25 系列；官方在线文档会演进，面试解释实际行为要以锁定版本及测试为准。不能用新版文档替旧 wrapper 的故障背书。

继续追问：升级 gate 至少覆盖 typed history round-trip、deferred 交接、pair-safe cutoff、错误消息/usage、provider reasoning 设置和异常 transcript；先做 provider-free，再做少量授权 live 兼容验证。

定位：pyproject.toml；src/affordance_runtime/model/policy/pydantic_ai_bridge.py

D38 · 如果明天不用 PydanticAI，哪里要改？什么时候值得换？

短答：主要替换 provider bridge、SDK history codec、工具定义与 deferred 交接、usage/trace 映射及 compaction/persistence 集成。TaskGoal、World、ActionPolicy port、Binder、Executor、Monitor 和 evaluator 合同保持稳定，但历史 checkpoint 格式不能假装天然兼容。

机制与证据

先定义迁移验收：同样模型/工具输入产生可校验提案；同 call_id 结果回填；不合法提案零执行；中断与恢复不重复副作用；摘要保留配对；每物理调用有 usage/错误记录。历史迁移需显式版本转换，不能把原始 wire 字段直接塞给新 SDK。

换型触发点应是已有证据：关键 provider 能力无法表达、升级维护成本持续超过收益，或出现真正需要持久图调度的产品需求。若只是另一框架更热门，不足以证明迁移值得。

继续追问：公平 PoC 先测五件事：动态目录、非法输出修复、外部执行交接、暂停后回填、长历史压缩。跑通 happy path 不能证明更易维护。

定位：src/affordance_runtime/model/policy/pydantic_ai_bridge.py；src/affordance_runtime/agent/policy.py

D40 · 和 DialogPilot 有什么区别？为什么一个多 Agent、一个单循环？

短答：DialogPilot 面向客服后端，核心是有界业务任务、证据覆盖、持久化准入与回答发布；GUI 项目面对不断变化的外部页面，核心是当前世界、动作效果与控制权。拆分依据是事实与执行边界。

机制与证据

DialogPilot 可以将独立领域任务交给 Worker，经 TaskGraph/Coverage 汇总；这里多个角色若同时认定页面状态或发动作，会增加控制冲突，因此只有一个 ActionPolicy。视觉补证不接管执行，两项目都让副作用与完成事实由明确 owner 产生。

继续追问：共性如何讲？模型负责语义，Runtime 保持事实与权限；但不能把 DialogPilot 的 PostgreSQL、多 Agent、Memory 能力挪到 GUI 简历里。

定位：DialogPilot 项目讲述；追问手册。

D41 · 为什么不用 LangGraph 或直接用更强的 computer-use 模型？

短答：本项目研究一个现成模型在更好的输入与控制支持下能完成多少任务，当前单步串行的外部副作用适合单循环。复杂持久图调度不是主要缺口，模型强弱则应作为可替换变量评测。

机制与证据

更强模型可能直接改善语义决策，专用 computer-use 模型可能改善视觉 grounding；但它们不自动解决过期引用、异常报告或任务评分。若专用模型在同条件质量/成本上更优，就通过 provider/grounding port 接入。

继续追问：你的创新是什么？是有证据支撑的系统组合与 owner 修复，不是新模型算法；当前没有公平全面对照就不称超越 SOTA。

定位：Agent S2；AgentOccam。
