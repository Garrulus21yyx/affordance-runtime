01 · Tell it at three depths

30 秒、3 分钟、10 分钟怎么讲

30 秒版本

可直接背 我做的是一个 Harness-first 的网页 GUI Agent Runtime。目标不是训练专用模型，而是让 DeepSeek V4 Flash 这种普通工具调用模型也能做跨站长任务。模型只看统一的公开世界并选择一个语义动作；Runtime 拥有工具合同、私有 binding、currentness、风险确认、执行、postcondition、checkpoint 和最终状态。结构化证据不够时，VLM 作为同一 World 的证据源按需开启。用户可以随时请求暂停、取消、修订目标或接管浏览器，Runtime 在最近合法边界确认，归还控制时必须先刷新世界。核心创新是把认知与控制 authority 分开，并用 BrowserGym / WebArena trace 验证 owner contract、held-out 行为与收敛；aggregate 泛化仍是开放证据。

3 分钟版本

  1. 动机：模型能力 ≠ 系统可靠性。通用模型会理解网页，却会调用过期元素、重复动作、把 executor success 当任务完成，也很难被外部用户安全中断。
  2. 设计：一个 loop，三个顶层真值。TaskGoal 是当前目标；fresh World 是当前环境；TaskEvaluator/native verifier 提供任务完成真值。Catalog、Binder、Executor、Monitor 等转换也各有唯一 owner；GoalPlan、模型 prose、Trace 都不是第二真相。
  3. 感知：多源输入，单一世界。DOM、BrowserGym、视觉、WoT、HTTP 由各自 SurfaceAdapter 投影并保留 lineage，再融合为 WorldObservation；VLM 不是平行 Agent。
  4. 动作：公开语义，私有执行。ActionPolicy 只看到当前 Catalog 和短生命周期 E-ref；Runtime 重新 admission、risk、binding、currentness，再由 Surface 执行。
  5. 闭环：动作之后才知道。每次 dispatch 后采 fresh World，ActionOutcome 只证明局部 UI 效果，TaskEvaluator/native verifier 提供完成或任务级失败事实；Monitor、用户和 Runtime 另行拥有控制终止。
  6. 协作：控制不是 kill thread。pause/cancel 在 safe boundary 收敛；revision 生成新 TaskGoal；takeover 发放 lease；return control 先重采世界。
  7. 证据：说清边界。provider-free 2284 tests；Task316 live success；Task798 的机械震荡已能 block，但 typed negative 的模型选择仍开放。

10 分钟版本

按本页顺序讲：问题定义 1 分钟、全链路 4 分钟、用户控制和视觉 2 分钟、SOTA 取舍 1 分钟、真实失败与证据 2 分钟。主线始终是“事实由谁拥有、转换在哪个边界发生、失败如何 typed fail-closed”。

02 · Problem framing

真正难的是长链路的语义与状态收敛

单步 click benchmark 只能说明 grounding。跨站任务会叠加页面切换、工具分页、长上下文、动态 DOM、provider 非法输出、副作用、用户干预和独立成功判定；任何一层 authority 混乱，模型再强也会“看见但做不到”。

World

模型看到的世界会过期

元素引用随 navigation / DOM revision 失效；历史里保留的 E-ref 不是可执行句柄。当前世界必须由 Surface 重新证明。

Protocol

模型输出不天然守合同

即使声明 parallel_tool_calls=false，provider 仍可能返回多个调用；必须在 provider 边界保存原始 attempt 并 typed reject。

Semantics

有变化不等于有进展

不同搜索、不同 read、甚至 DOM identity churn 都可能围绕同一失败中心震荡；恢复动作名不同不能洗掉累计失败。

项目命题不靠不断加 prompt、重试和 benchmark case 分支，而是把共享根因归还给正确 owner：Source 拥有事实、Catalog 拥有工具合同、Binder 拥有私有解析、Executor 拥有 dispatch、Evaluator 拥有任务完成证明、Monitor 拥有机械 recurrence。

03 · Architecture

一套 Harness，三条互相校验的链

Data plane

TaskGoal + World → AgentContext → Decision → Receipt + fresh World → Evaluation。解释每个对象如何变形。

Control plane

PublicSession → TargetRuntime → CoreAgentLoop。解释谁推进 step、何时停、何时让用户介入。

Authority plane

目标、环境、合法动作、执行结果、完成判定各有唯一 owner；Trace/Shell 只观察或投影。

单一 dispatch authority，不等于只调用一个模型GoalCompiler 只在 start/revision 生成静态 advisory GoalPlan；VLM 只返回带 lineage 的视觉证据；TaskRevisionCompiler 只生成完整 replacement proposal。恢复时没有独立 StrategyRevision：typed recovery signal 直接让同一个 ActionPolicy 进入 deliberate profile。以上角色都不能 dispatch，也不能证明任务成功。

04 · End-to-end code path

从用户一句话到任务终止的完整链路

这一节是面试叙事版要看 BrowserGym/Playwright 分工、raw observation、E-ref binding、动态 ToolCatalog、PydanticAI envelope、Harness compaction 与用户控制的逐对象源码版，请打开 实现链路逐层拆解 →
  1. 1. Session 接收有 currentness 的命令。PublicSessionCommand 带 command_id + expected_task_revision + expected_run_status；重复 ID 同 payload 幂等，不同 payload 冲突。入口不是随便调一个 runtime 方法。
  2. 2. Intake 建立 TaskGoal。TaskGoal 保存 instruction、constraints、allowed/forbidden effects、success criteria、requested outputs、risk profile、budget 和 revision；它描述“要什么”，不描述 selector 或步骤。
  3. 3. Composition 组装唯一 Runtime。compose_target_runtime_from_environment 创建 model roles、ActionSpaceBuilder、Binder、ContextBuilder、RiskPolicy、GoalCompiler、TaskRevisionCompiler、EpisodeMonitor 和 CooperativeRunControl，注入同一个 TargetRuntime。
  4. 4. Environment reset 产出初始 World。ObservationAcquisitionCoordinator 根据 typed need 选择 source；各 SurfaceAdapter 把 DOM/BrowserGym/visual/WoT/HTTP 投影为统一 contract，Fusion 保存 source lineage，不让 CoreLoop 解析 provider 协议。
  5. 5. GoalCompiler 只在 start/revision 稀疏调用。它可返回 Ready / NotRequired / NeedsInput / Unsupported / Failed。Ready 中最多 8 项，仅有 id/objective/done_when/depends_on/final。Runtime 校验边界，不计算 item progress；失败时继续普通 loop。
  6. 6. 初始化唯一 RunState。保存 current World、task evaluation、step budget、静态 goal resolution、delivery store、recovery signal、monitor snapshot 等控制事实。Checkpoint 是它在 committed boundary 的 typed projection，不是序列化 coroutine。
  7. 7. 每一步先构造完整 ActionSpace。ActionSpaceBuilder 从 TaskGoal 与 current World 生成语义 option，再由 WorldDeliveryIndex / ActionDeliveryPlan / GroundedToolCatalog 决定本轮可见子集和 resolver rows。
  8. 8. ContextBuilder 产生唯一模型输入。输入是 TaskGoal、GoalPlan、fresh public World、bounded recent outcomes、current tools、recovery/control feedback 和 final response codec。历史不能把旧 E/R/N/F ref 重新变成可执行句柄。
  9. 9. DeepSeek 选择且只选择一个 decision。支持 SelectAction、RequestObservation、find/read/search local tool、AskUser、FinalResponse、Wait、Abort。PydanticAI bridge 拥有 provider envelope、exactly-one-tool-call、重试预算与 transcript。
  10. 10. Runtime 在 dispatch 前逐门校验。Catalog/ActionSpace admission → recovery replay guard → RiskPolicy → Confirmation → Binder → environment currentness。任何失败都是 typed outcome；模型不能凭 prose 构造 action ID、selector 或坐标。
  11. 11. Surface 执行动作并收集 fresh post-world。BrowserGym/Playwright 是成熟的底层执行 owner。DispatchStatus 区分 NOT_SENT / SENT / SENT_UNKNOWN；发送未知时不能盲重试未知副作用。
  12. 12. 两级验证关闭动作分支。ActionOutcomeProjector 判断局部 UI change/postcondition；TaskEvaluator 或 native verifier 判断全局任务。StepResult 按 decision 分支携带 before/after World、可选 receipt/effect/evaluation、typed failure 和 lineage；local/control 分支不伪造执行 receipt。
  13. 13. Monitor 在 commit 后判断机械收敛。它不理解业务语义，只观察 owner-produced transition/result identities。未解决 failure center 穿过不同 recovery 动作继续累计；有真实新 World、新信息或 verified GUI progress 才关闭。
  14. 14. Loop 继续或在闭合状态终止。RUNNING 进入下一轮；WAITING_USER / WAITING_CONFIRMATION 暂停在有类型交互；DONE / BLOCKED / CANCELLED / FAILED 结束。Trace 与 SSE 只投影已产生事实。

第 9 步不是“永远 click”：closed decision algebra 如何分流

StepResult = {
  decision, before_world, after_world, status_after,
  task_evaluation?, execution_receipts?, action_outcome?,
  observation_outcome?, runtime_failure?, control_termination?
}

异常路径也不折叠：provider/schema failure 形成 PolicyFailure；dispatch 前失败是 NOT_SENT，可以在 fresh context 重新选择；SENT_UNKNOWN 表示外部效果可能已发生，必须观测/对账或人工介入，禁止盲重试；dispatch 后采集失败与动作失败也分别保留 owner。

一次跨站任务的关键转折网站切换不会触发 replan，也不会创建第二 Agent。新的 URL/DOM 由 Surface 形成新的 World；同一个 ActionPolicy 在下一轮重新解释 GoalPlan 与 fresh World。跨站能力来自统一公开协议，而不是每站 adapter 写任务规则。

06 · Ordinary DeepSeek inside a strict harness

为什么普通 DeepSeek V4 Flash 能接入，而模型又不是系统中心

DeepSeek 官方 API 采用 OpenAI/Anthropic 兼容格式，V4 Flash 支持工具型 Agent 场景；仓库通过 OpenAICompatibleModelPort 统一 transport，再由 PydanticAI bridge 处理模型消息和工具调用。接口适配直接，但兼容 wire 不代表行为合同天然可靠；本项目尚未完成同条件成本、延迟与成功率 A/B。

模型负责的

解释任务、选择证据需求、在当前工具中选一步、处理语言与开放世界歧义、在必要时生成最终内容。

模型不负责的

元素 currentness、selector/坐标、能力授权、风险、执行结果、任务完成、checkpoint、user lease、Monitor 状态。

Harness 给它的增益

更小且当前的 action catalog、typed tool return、结构化 World、短期 recovery feedback、pair-safe history、独立 evaluator。

Harness 不能凭空补的

模型可能仍拒绝完整否定证据、选错可用 route、违反 exactly-one-call，或在真实进展上极低效；这些必须通过 live benchmark 暴露。

为什么 provider 违规不能“取第一个 tool call 就算了”多个调用可能互相依赖或产生两个副作用。选择其中一个会把 provider 非法输出变成 Runtime 猜测。当前边界保存每次 physical response，做一次有界完整 retry，仍非法则 typed invalid_response 失败。

07 · Selective multimodality

VLM 什么时候开：按证据义务，不按“撞墙了”

默认结构化路线更可定位，也更容易证明 currentness；视觉用于结构源无法诚实回答的视觉问题。它预计能减少不必要的图像 token 与调用延迟，但项目尚未完成同条件 A/B；配置了 VLM 只是 capability，不是调用理由。

08 · External user control

中断、撤销、修改、接管不是四个按钮，而是四种状态语义

外部用户可在运行中随时发出请求，但“请求已接收”不等于“控制权已经切换”。Runtime 只在最近合法语义边界确认，避免截断 provider/tool pair、掩盖未知副作用或持久化半步状态。

USER
pause(command_id, expected status)：请求进入 CooperativeRunControl，不直接杀 task。
CORE LOOP
在 BEFORE_POLICY / AFTER_POLICY / AFTER_EVALUATION / WAITING_* 等安全边界 acknowledge；若 action 已发送且结果未知，不能伪造干净暂停。
CHECKPOINT
捕获 TaskGoal、committed RunState facts、model history、monitor snapshot 和 reconnect reference，SQLite 原子提交后才宣布 paused。
USER
revise：完整新目标提案；take_over：消费 checkpoint 并签发 live input lease；cancel：停止未来控制。
RUNTIME
修订评估既有副作用是否已满足、可补偿、未知或不可补偿；没有通用 rollback 幻觉。
RETURN
撤销用户 lease → fresh capture → 重建 current action space → Agent 继续；刷新失败则 manual control 恢复为新 lease。
“撤销”的真实边界软件不能保证任意外部网站副作用可回滚。项目支持的是：若 owner 明确提供合法 compensation route，进入 effect reconciliation；否则返回 typed non-compensable / unknown / needs-input。Cancel 只保证不再发新动作。

09 · Root-cause convergence

为什么之前能发现 stall，却始终察觉不了震荡

旧机制把 RecoverySignal 同时当“给模型一次提示”和“失败累计的生命周期”。信号被下一次 read/search/observe 消费后，Monitor 没有保留同一 unresolved center；模型换一个 recovery 动作，累计就归零。于是 S → A → S → B → S 每次都像新的 attempt 1。

症状级修法

加 retry 次数、加更长 short-cycle window、枚举 search/read 组合、在 prompt 里强调“别重复”。它们只能覆盖已知波形。

VS

owner 级修法

EpisodeMonitor 持有 bounded unresolved failure center；signal 只是当轮反馈。不同无进展动作加入同一 center，重新进入成员或容量耗尽就 typed block。

正向 escape contract 只有 owner-produced progress：fresh public semantic digest、NEW_INFORMATION、verified operational GUI result、native terminal、task revision 或 episode reset。动作名、query、region、result 语法、recovery epoch、model profile 改变都不算进展。

Checkpoint v8 保存 Monitor snapshot，恢复时只有 fresh World semantic digest 相同才恢复该 center。它不会进模型上下文，也不会记录“模型已经完成了某个里程碑”。Task798 live repeat 证明同一个 center 的 attempt 从 1 到 2，并在 18 步 control_stalled，不再跑满 8 分钟。

恢复推理仍由唯一 ActionPolicy 完成：active recovery 只改变同一 policy 的 deliberate 调用 profile，并要求有界 decision basis；生产代码没有 StrategyRevision、独立 reviewer 或第二套 history。Monitor 只提供机械事实与硬约束，不能替模型选择业务 route。

10 · SOTA alignment and deliberate differences

与当前 computer-use 路线对齐，但不盲目复制

这里比较的是架构方向，不是宣称本项目成绩超过专用模型。2026 年的一手资料共同确认：最终都需要“模型—客户端执行环境—新观察”的闭环；差异在模型是否专训、观察与动作表示、验证和用户控制由谁拥有。

为什么不是 Manager / Worker 多 Agent

当前失败主要来自世界投影、工具可发现性、provider contract、currentness 和 recurrence authority；增加 manager 不会修复这些 owner 缺口，反而产生第二计划、第二历史和委派失败。只有 benchmark 明确证明单 policy 的认知职责不可兼容，才值得新增 specialist；视觉就是 specialist，但它只返回证据，不接管控制。

为什么不用 memory / RAG / RL data flywheel

当前跨站任务的关键状态是 fresh World 和有限的 task-required facts，不是开放域知识库。仓库的 Harness compaction 保留 pair-safe outcomes 和必要事实，删除过期 executable refs。长期 memory 可能让旧世界重新获得权威；训练与 RL 又超出项目范围。研究界正在用 world model 与 RL 扩展 Web Agent，但那是模型能力路线，不是本项目当前的 runtime invariant 缺口。
