# M8.6 G1 Unified Proposal Validation and Compatibility Containment

Date: 2026-07-23

## Decision

G1 now has one source-neutral semantic proposal validation boundary in the
normal Coordinator path. This is material progress, not G1 closure: broader
paraphrase/distractor/ambiguity controls and extraction or removal of the
dormant task-shaped algorithms from `generalist_planner.py` remain open.

## Runtime change

`PlannerProposalValidator` validates every semantic proposal before completion,
clarification, contract binding, capability/approval handling, or execution.
The same call site receives proposals from:

- the strict LM planner;
- explicit historical compatibility compilation;
- parent-agent planner adapters;
- accepted TaskSkill exposure;
- future recovery strategies that return `PlannerProposal` through the same
  Coordinator boundary.

The validator rejects stale task/state/snapshot identity, missing or
action-incompatible targets, targets attached to non-target actions, unexpected
destinations, and identical drag endpoints. `ContractBuilder` retains its
defensive binding checks; it is no longer the first proposal validator.

Successful validation emits `PlannerProposalValidated` before
`PlannerProposalProduced` and `ContractBuilt`. Rejection emits the typed
rejection code and validation boundary. Accepted-skill proposals use this same
trace event and still fall through to System 2 on rejection.

No proposal can add capability or approval data: the Pydantic semantic schema
continues to reject those fields, and Coordinator-owned contract policy,
capability gate, approval binding, approval-state reobservation, preflight,
execution, and verification remain unchanged.

## Strict and compatibility behavior

- `strict-generalist` preserves `ask_user` when current page evidence does not
  establish one safely scoped action. A resolved intake ambiguity flag alone no
  longer removes clarification.
- form-cardinality, prefix/suggestion, and disclosure-shaped instructions call
  the strict model and may safely clarify; they do not execute a compatibility
  compiler before the model.
- the same fixtures demonstrate the old deterministic behavior only when
  `historical-compatibility` is selected explicitly.
- the declarative historical registry moved from the misleading
  `default_semantic_compilers.py` name to
  `compatibility_semantic_compilers.py`; strict mode cannot load it.
- strict and compatibility use separate frozen Prompt identities:
  `generalist-planner-strict-v1` and historical `generalist-planner-v59`;
  BrowserGym checkpoint metadata records the profile-selected Prompt;
- the strict Prompt contains no autocomplete, slider, long-text-boundary, or
  other task-family recipe;
- strict candidate binding never repairs missing option values, rewrites text,
  selects remaining multi-select values, or redirects an option target from
  task wording;
- strict candidate validation and repair use only action/schema compatibility,
  current semantic targets, verifier-backed satisfied pairs, and an exact
  blocked-progress signature. Historical objective parsing, terminal exposure,
  prefix/direction repair, and semantic rewrites are compatibility-only.

At the time of this proposal-validation slice, historical algorithms still
resided in the large Generalist module. That limitation is superseded by
`m8.6-g1-physical-containment-20260723.md`, which records their physical
extraction and the strict non-loading controls.
