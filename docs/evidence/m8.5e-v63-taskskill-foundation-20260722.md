# M8.5E v63 TaskSkill Foundation Evidence

Date: 2026-07-22

## Scope

This slice implements the semantic TaskSkill schema, verified-success mining
gate, quarantine lifecycle, incremental step exposure, and replay acceptance
policy. It does not claim that a real held-out TaskSkill has already been
accepted or that Coordinator System 1 selection is complete.

## Schema and safety boundary

`TaskSkillPayload` contains a versioned trigger, typed parameters, ordered
`SkillStep` values, semantic source/destination target queries, action intent,
preconditions, invalidation rules, postconditions, evidence requirements,
capabilities, approval/risk declarations, applicability, source traces,
variants, negative examples, and a held-out suite.

Validation rejects raw selectors, XPath/CSS, BrowserGym bids, DOM indices,
marks, screenshot refs, coordinates, URLs, browser handles, and approval
tokens. Payloads are SHA-256 digest-bound and loaded through the existing
evolution runtime only after acceptance.

## Verified-success mining

- Source traces must be independently verified and have zero policy violations
  and verifier false accepts.
- Mining requires at least three traces across at least two layout/environment
  variants.
- All traces must share one semantic step shape. Differing semantic labels and
  action values become typed parameter slots instead of stored locators.
- Every step requires independent postcondition evidence.
- Every mined artifact is persisted as `QUARANTINED` before replay.

## Incremental execution boundary

- An accepted payload exposes exactly one semantic `PlannerProposal` for the
  current observation and state version.
- Current `UnifiedAffordance` role, label, and supported action must resolve to
  exactly one target; drag also requires one distinct destination.
- The executor does not create a low-level action or grant authority. Unified
  Route, ContractBuilder, policy, preflight, execution, and verification remain
  downstream.
- Progress advances only through `checkpoint_verified`. A mismatch or failed
  verification preserves prior completed steps/evidence and records fallthrough
  for later System 2/Recovery handling.

## Replay gate

Acceptance requires successful independently verified `original`,
`task_family`, `heldout`, `global_smoke`, and `safety_smoke` categories, task
success 1.0, zero policy violations, verifier false accepts, and duplicate
effect risk, activation precision 1.0, plus reduced model calls or latency.
Missing held-out evidence or no efficiency gain leaves the artifact
quarantined. Accepted artifacts remain rollbackable through the existing
registry/runtime mechanism.
