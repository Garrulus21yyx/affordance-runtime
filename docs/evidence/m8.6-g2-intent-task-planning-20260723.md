# M8.6 G2 Intent and Task-Planning Integration Evidence

Date: 2026-07-23

## Boundary implemented

The Runtime keeps intent compilation, task planning, step planning, grounding,
contract binding, execution, and verification separate. `IntentDraft` carries
a typed flat/multi-stage routing hint. `IntentDraftValidator` creates the
immutable TaskSpec and derives its maximum operation class and requested
capabilities from sourced requested effects; none of those requests grant a
capability.

`RunCoordinator` installs `PlanningRouter` for TaskSpec runs. Flat tasks receive
one synthetic verifier-backed subgoal. Multi-stage tasks require an explicitly
configured `LLMTaskPlanner` or another accepted planner and fail closed when no
complex planner exists. `GeneralistTaskPipeline` and the BrowserGym generalist
entrypoint attach the same model-backed complex path while leaving flat tasks
on the rule planner. The reference CLI uses the common router when structural
verification is enabled; explicitly loaded compatibility profiles that disable
structural verification do not pretend to advance a TaskPlan.

## Evidence and safety behavior

Coordinator binds verifier specs to current TaskPlan criterion and evidence
requirement IDs after every contract builder, including adapter-specific
builders and trusted preflight rebinding. Existing SkillStep identities remain
bound while also satisfying the active subgoal. An explicit binding to another
subgoal is never rewritten.

An adapter-declared terminal success is recorded as strong external-evaluator
evidence. A normal revision/state delta remains weak and cannot independently
complete mandatory progress. An evidence-explicit `blocked`, `incomplete`,
`inconclusive`, or `unsupported` no-effect terminal can stop safely, but is
traced as `TaskPlanStoppedIncomplete` and never represented as TaskPlan
completion.

The first explicitly requested medium-risk action does not require an
idempotency key or compensation merely to execute. `BoundedRecoveryPolicy`
still permits retry only with an idempotency key and continues to inspect an
uncertain effect before any repeat.

## Context leakage controls

- Step-planner TaskSpec summaries omit task ID, request/source references, and
  creation metadata.
- Task-planner model/trace summaries omit the same identities and expose only
  URL origin, not path/query task names.
- Artifact paths exposed to the step planner are opaque SHA-256 references.
- BrowserGym tests assert absence of suite task identity and official reward
  vocabulary while preserving typed operation class, targets, and structure.

## Normal multi-stage proof

`tests/test_task_pipeline_multistage.py` starts from a raw non-BrowserGym user
request. The intent model emits a sourced multi-stage draft; the common router
uses `LLMTaskPlanner`; Coordinator executes `discover` then `confirm`; fresh
strong observation evidence completes each subgoal in dependency order. No UI
selector, coordinate, capability grant, or approval enters the TaskPlan.
