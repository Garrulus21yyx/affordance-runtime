## Scope and authority boundary

The Runtime now normalizes failures through one strict `FailureEnvelope` and
selects one validated typed `RecoveryPlan`. `RecoveryCoordinator` is a pure
decision boundary. It cannot write Runtime phase/state, capture observations,
create planner proposals, bind contracts, grant approval, execute effects, or
verify outcomes. `RunCoordinator` remains the sole phase writer and delegates
each command to the port that already owns the operation.

This slice adds no benchmark-family policy, task-specific repair, provider
special case, `.env` dependency, remote workflow, benchmark run, or score
claim.

## Implemented protocol

- `FailureEnvelope` records phase/class/signature, state and observation
  lineage, effect status, rejected assumptions, attempted strategies, semantic
  progress fingerprint, artifact references, and remaining recovery budgets.
- Exact signatures remain available for debugging while semantic-family keys
  intentionally exclude volatile target, selector, backend, and snapshot
  identity used by loop detection.
- Typed commands cover clarification, observation/evidence repair, task/step
  replanning, grounding/routing, context/provider/schema changes, approval,
  post-state inspection, idempotent retry, compensation, and safe termination.
- `RecoveryPlanValidator` rejects stale, unavailable, repeated, over-budget,
  provenance-forged, unsafe retry/reroute, unproven compensation, and no-op
  plans.
- Every successful command emits a `RecoveryCommandReceipt` and non-empty
  `RecoveryDelta`; a failed command emits a failed receipt and no delta.
- `REPLAN_TASK` and `REPLAN_STEP` remain pending until a replacement TaskPlan
  is accepted or a new semantic proposal is validated. Merely deciding to
  replan is not recorded as successful recovery.
- Uncertain effects enter post-state inspection before any repeat. A retry is
  possible only with a matching idempotency key and proof that the prior effect
  was not dispatched or did not occur.
- Accepted recovery artifacts must be explicitly present in the loaded profile
  identity and digest. Missing or forged artifact provenance falls through to
  built-in policy.

## Phase and behavior evidence

Unit and integration tests cover intake clarification, observation failure and
source conflict, task planning, step planning, proposal validation,
grounding/binding, preflight stale/conflict handling, execution uncertainty,
verification repair, provider defer, skill activation, semantic loop stopping,
accepted-profile provenance, and lower-half adapter compatibility.

Representative recovery traces prove:

- `FailureDetected -> RecoveryStrategySelected -> RecoveryCommandStarted`;
- owning-port work occurs before successful command completion;
- `RecoveryCommandCompleted -> RecoveryDeltaValidated ->
  RecoveryReenteredPhase` only after a real changed result;
- an equivalent planning failure changes strategy once and aborts before
  exhausting the recovery budget;
- uncertain execution is inspected and never blindly duplicated;
- unavailable safe change ends in clarification, defer, or abort.
