# M8.2B v149 Daily Calendar Range Binding

Date: 2026-07-22

## Boundary repaired

The release rescan first grouped `daily-calendar` with the remaining empty
observation failures. Its authored page contains 48 half-hour cells, including
cells outside the current viewport, and creates an event through a pointer
range followed by an event-name field and a terminal Create control.

The repair does not put bids or coordinates into `PlannerProposal`. The DOM
adapter derives two semantic endpoints for every coherent half-hour cell: a
drag-capable start boundary and a distinct drop-capable end boundary. This is
important for a 30-minute event, where both semantic endpoints share one
authored cell/bid but Core must still reject identical semantic targets.

`GestureContractBinder` resolves both endpoints before backend encoding and
owns the generic invariants:

- source and destination semantic targets differ;
- both endpoints come from one observation epoch and page revision;
- both leases and target fingerprints are current;
- the source supports drag, the destination accepts drop, and both share the
  selected route;
- blocking overlays, capability, risk, approval, contract hash, and trace
  remain part of the ordinary Core path.

`ActionContract.gesture_binding` carries both endpoint identities, locators,
snapshots, fingerprints, and leases. Its canonical hash therefore binds both
targets; approval tokens bind that hash, and `ActionContractBound` traces both
source and destination. BrowserGym only translates the validated binding. For
the calendar it uses a bid-bound pointer lifecycle; Playwright and Visual keep
their existing `drag_to` and pointer encoders.

The bounded Planner projection was also made action-family diverse. Repeated
calendar endpoints can no longer crowd the dynamically-created event-name
field and Create terminal out of the fixed context budget. This is a generic
bounded-context rule and contains no task ID, selector, bid, or coordinate.
