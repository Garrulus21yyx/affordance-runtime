# M8.2B v103 Immutable Run Identity Gate

Date: 2026-07-22

## Finding

The frozen nightly already rejected a dirty worktree, but the release profile
did not. Dirty diagnostic checkpoints also stored only the current Git commit
and `working_tree_clean=false`; two different source edits on the same dirty
commit could therefore compare as the same resumable run identity.

## Repair

- checkpoint metadata advances to `browsergym-generalist-checkpoint-v5`;
- run identity now includes `source_tree_sha256`, derived from runtime Python
  sources, the isolated launcher, `pyproject.toml`, and pinned requirement
  files;
- `.env`, documentation, artifacts, and benchmark output directories are not
  read by or included in that digest;
- both `nightly` and `release` reject a dirty worktree before BrowserGym
  import, source preparation, local source-server startup, or episode execution;
- changed executable source makes checkpoint metadata differ, so `--resume`
  requires a new output directory.

The repository-local `.env` is also confirmed ignored by Git and absent from
the tracked file set. No secret value was printed or written to evidence.

## Validation

- focused BrowserGym adapter/launcher tests: `55 passed`;
- full repository after the immutable-identity and fail-fast assertions:
  `344 passed`;
- full Ruff: clean;
- mypy over BrowserGym production/launcher modules: clean;
- `git diff --check`: clean;
- local Ollama health endpoint: reachable;
- GitHub Actions and remote providers: not used.

## Boundary

This closes the executable immutability guard, not the frozen score. The
current worktree is intentionally dirty and the runtime correctly refuses to
start a nightly/release claim from it. The next score-bearing run requires a
user-approved clean committed revision and a fresh output directory.
