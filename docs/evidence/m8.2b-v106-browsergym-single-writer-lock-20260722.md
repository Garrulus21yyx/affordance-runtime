# M8.2B v106 BrowserGym Output Single-Writer Lock

Date: 2026-07-22

## Observed failure

Several stale diagnostic launchers were found concurrently targeting the same
checkpoint directory. Immutable metadata prevents incompatible resume, but it
did not prevent two compatible processes from selecting and writing the same
unfinished episodes concurrently. This can duplicate browser/model work and
corrupt the meaning of checkpoint progress.

The identified legacy process groups and their Playwright children were
terminated explicitly. Local Ollama remained running. Their partial diagnostic
outputs were not promoted to evidence or scores.

## Repair

The sole BrowserGym launcher now acquires two non-blocking advisory locks before
dotenv loading, runtime preflight, source preparation, or child startup and
holds both until the benchmark child exits:

- `<output>/.browsergym-run.lock` prevents two writers from sharing one
  checkpoint directory;
- `$XDG_RUNTIME_DIR/browsergym-generalist.lock` (with a per-user `/tmp`
  fallback) serializes different output matrices that share the local browser,
  Ollama model, and GPU;

- a concurrent launch for the same output fails immediately with exit code 2;
- a released directory can be resumed normally;
- a concurrent launch using another output directory is also rejected while a
  local matrix owns the shared runtime;
- the lock contains only the local launcher PID and is emptied on release;
- no `.env` value enters the lock or error message.

## Boundary

The output lock protects checkpoint ownership; the per-user global lock protects
the shared local execution runtime. Parallel BrowserGym matrices on the same
user runtime are intentionally unsupported because they make latency and model
service evidence non-comparable.
