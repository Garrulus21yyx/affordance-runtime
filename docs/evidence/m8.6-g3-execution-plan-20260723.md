# M8.6 G3 Full-Phase Recovery Execution Plan

Date: 2026-07-23
Status: complete

## Goal and fixed boundaries

Close G3 without introducing a second state machine or granting recovery direct
execution authority. `RunCoordinator` remains the sole state/phase writer.
`RecoveryCoordinator` may normalize failures, select and validate one typed
command, and declare re-entry; the owning Runtime port executes the command.

Recovery cannot infer missing world state, mutate an old contract/snapshot,
repeat an uncertain effect without inspection, create benchmark-family policy,
or expand task authority. Accepted recovery profiles load explicitly by digest
and may influence strategy selection only through the same validators.

No benchmark episode matrix, GitHub Action, `.env` access, or push belongs to
this implementation phase.

## Initial audit findings

- `FailureSignature`, `RecoveryIncident`, `RecoveryCascadeDetector`, and
  `RecoveryHandler` currently cover the lower half around a built contract.
- `RecoveryAction` is too narrow for phase-general commands and current
  decisions do not carry a validated `RecoveryDelta` or declared re-entry.
- Coordinator directly owns recovery state today; that authority must remain
  there while selection/validation moves behind one pure decision boundary.
- G2.5 already supplies typed active perception; G3 must request it by command,
  not duplicate its controller or observation loop.

## Completion decision

G3 is complete. Recovery selection is phase-general and pure; it does not own
state mutation, observation, planning, binding, approval, execution, or
verification. A command is not recorded as successful until its owning port
produces the promised changed evidence, plan, route, execution, or terminal
state. Failed replanning produces a failed receipt without a delta before the
next strategy is selected. G4 complete-run audit and G5 generalization evidence
remain pending and are not implied by this closure.
