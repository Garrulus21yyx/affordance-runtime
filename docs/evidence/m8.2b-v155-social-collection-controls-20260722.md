# M8.2B v155 Social Collection Controls

Date: 2026-07-22

## Failure attribution

The v133 rescan found authored controls in `social-media`,
`social-media-all`, and `social-media-some`, but the DOM adapter exposed either
no actions or only the native Submit button. BrowserGym represents these as
custom `span`/`li` elements with a `bid`, owner text, collection position, and
an authored action class. Promoting every unmarked `bid` would weaken the
observation boundary, so this was a shared `OBSERVATION / CONTEXT` contract
gap, not a provider or Prompt failure.

The first repaired slice exposed a separate adapter issue. The planner selected
the correct owner's More control, but ordinary locator click only brought an
off-screen item in the nested collection into view. The page did not change,
and the no-repeat guard correctly blocked blind retries. This was a BrowserGym
activation-route issue, not a reason to weaken duplicate-effect protection.

## Generic repair

The DOM adapter now recognizes only a bounded authored collection shape: a
current `span` or `li` with `bid` and one action class, an enclosing `.controls`
region and `data-result` item, and exactly one owner token. It records current
action, owner, one-based position, and toggle state in affordance state and
fingerprint. Explicitly hidden menu descendants remain excluded.

The rule compiler resolves owner/action semantics, opens the unique current
More control when needed, and then selects the newly observed menu item. Batch
variants toggle only required currently-unselected controls and submit only
after the requested count is satisfied. No task ID, selector, bid, or coordinate
enters a Planner proposal.

BrowserGym keeps backend translation. Authored collection controls use its
current-bid DOM-click lifecycle after `scrollIntoView`; ordinary controls retain
the standard typed click path. Every action still uses a fresh observation,
ActionContract, preflight, verifier, trace, and no-repeat guard.
