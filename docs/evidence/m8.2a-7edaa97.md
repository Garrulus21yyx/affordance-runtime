## Clarification, Revision, and Failure Boundaries

- Blocking ambiguity returns `NEEDS_CLARIFICATION` before planning.
- `TaskRuntimeService.revise_task` accepts only a higher immutable TaskSpec
  revision, clears execution/approval state, and stale proposal revisions are
  rejected by `ContractBuilder`.
- Requested capabilities remain distinct from caller grants. A planner cannot
  create a grant, approval token, backend, selector, coordinate, or WoT form.
- Compiler errors emit `IntentCompilationFailed`; model parse failures contain
  only schema paths/error codes; planner failures emit
  `PlannerProposalRejected`; runtime failures remain separate Coordinator
  error codes.

```text
runtime_status=done
official_success=true
official_reward=1.0
action_count=1
action_family=click

```

The generalist BrowserGym contract builder maps only `activate`, `type_text`,
and `select_option` to typed BrowserGym actions using an affordance `bid`.
Official reward/success are derived from environment termination/reward, not
from a planner result field.
