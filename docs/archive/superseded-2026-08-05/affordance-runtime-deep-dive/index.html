SECTION 01

一页读懂：它到底是什么

先建立正确心智模型，再进入类、字段与调用关系。

Affordance Runtime 是一个“权威在 Runtime、模型只做受限提议”的任务执行内核。它接收自然语言或父 Agent 提交的任务，将其编译为带来源、约束、义务和证据要求的 TaskSpec；再生成步骤计划，循环感知、规划、执行、验证和恢复，直到有独立证据支持任务完成，或以明确原因停下。

代码真实实现

五阶段循环、单写者状态提交、严格 Planner 候选选择、快照绑定、能力与审批门、独立后验验证、类型化失败路由、因果 Trace DAG、外部任务级工具接口。

不要误读

模型不拥有 TaskSpec、TaskPlan 版本、坐标、能力、审批和完成判定；执行器返回 success 也不代表任务完成；仓库没有通用聊天历史滚动摘要器。

最短 E2E 路径

UserRequest→SourceLedger→IntentDraft→TaskSpec→TaskPlan / StepSpec→PlanningRequest→ActionChoice→ActionContract→ExecutionReceipt→VerificationReport→TaskResult + Evidence
贯穿全报告的核心问题每个阶段都要回答四件事：输入是什么？谁有权决定？状态由谁提交？结论靠什么证据成立？

三条不能混淆的链

DATA PLANE

数据链

文本逐步变成有类型对象；页面逐步变成可验证证据。它回答“系统知道什么”。

CONTROL PLANE

控制链

Coordinator 选择下一阶段，预算与失败所有者决定继续方式。它回答“下一步由谁做”。

AUTHORITY PLANE

权威链

TaskSpec、Plan Authority、CapabilityGate、RuntimeCommitter 和 Verifier 限制模型权力。它回答“谁说了算”。

入口与外层调用：谁能把任务送进来

同一个 Runtime 有多种外壳，但进入内核后收敛为同一套协议。

入口提交对象调用路径边界意义

稳定任务 APITaskRequestTaskRuntimeService → TaskRunner支持 submit、execute、revise、approve、cancel、result、evidence、trace

RunRequest 是不可变运行信封，含 task_id、goal、target、约束、能力和可选 task_spec。如果传入 TaskSpec，任务 ID 与目标必须一致，避免外层信封偷偷覆盖规范语义。RuntimeStep 则把运行状态显式化为 observing、planning、preflight、waiting_approval、acting、verifying、recovering、done、failed 等状态。

为什么只给父 Agent 任务级工具？若父 Agent 同时拥有 click/type 和任务 API，它就能绕过 Runtime 的 TaskSpec、审批、快照租约与验证链。这里通过“工具面物理隔离”缩小越权空间，而不只靠 Prompt 告诫。

SECTION 04

自然语言如何变成可执行语义

关键不是抽取几个槽位，而是建立来源、授权、义务和完成证据之间的可证明关系。

查看自然语言编译逐步转换与语义损失

4.1 编译流水线

  1. 接收 UserRequest：raw_text 配合 conversation、attachment、target、profile 的引用和调用者、渠道、语言、时间信息。
  2. 建立 SourceLedger：代码按整段与子句切出 source unit，记录文本范围、哈希、敏感性；引用型上下文只暴露标签与哈希，不自动把隐私内容塞给模型。
  3. 模型产生 IntentDraft：抽取目标、实体、请求效果、偏好、输出、成功条件、证据、约束、语义值、来源声明、禁止效果和歧义。这个草稿被明确定义为“不可执行”。
  4. 代码规范化义务图：CanonicalObligationCompiler 重建 claim/obligation ID、依赖、值传递和类型化证据要求；模型提供的 ID 不继承权威。
  5. 确定性准入：验证 objective、effect、success criterion、source authorization、能力、风险、歧义和覆盖。必要时做有界 schema 修复；可选模型审阅者只有否决权，没有放行权。
  6. 生成 TaskSpec：不可变、可哈希、有 revision 的规范任务。结果可能是 READY、NEEDS_CLARIFICATION、POLICY_CONFLICT 或 UNSUPPORTED。

4.2 一个字段级示例

用户：把搜索结果中第二本书加入购物车，但不要购买。

IntentDraft（模型提议，不可执行）
  objective: "将指定书加入购物车"
  requested_effects: [add selected book to cart]
  entities: [search results, second book, cart]
  constraints: [no_purchase]
  ambiguities: []

TaskSpec（Runtime 规范化并授权）
  operation_class: effectful
  obligations:
    - locate-result-2     # 谓词义务：第二项被当前观测唯一识别
    - add-to-cart         # 效果义务：依赖前者，要求后验状态证据
  forbidden_effects: [purchase]
  success_criteria: [cart contains selected book]
  capabilities: [cart.write]  # 只能来自调用边界授予，不能由模型自授

这里的 obligation（义务） 是带来源的目标状态或效果节点：它有 subject、relation、expected value、依赖、证据要求、是否阻塞、是否终端等字段。义务图让“完成任务”从模糊文本变成可检查的依赖闭包。

深挖：为什么 SourceLedger 不是普通 Prompt 引用？

它把每个语义断言追溯到代码拥有的 source unit。后续 canonical compiler 与 coverage validator 能证明：所有必须覆盖的用户来源最终落在结构有效的终端义务图上。模型不能凭空增加效果，也不能用自己生成的字符串 ID 冒充授权来源。

深挖：父 Agent 已经结构化了语义，还要再编译吗？

ParentSemanticProposalCompiler 可以跳过一次模型抽取，但父 Agent 的结构化提案仍是“不可信输入”。Runtime 仍重建来源谱系、规范 ID 并走相同验证与覆盖流程。这是 trust boundary，而不是重复劳动。

源码：task_intake.py · intent_compiler.py · canonical_obligation_compiler.py

SECTION 05

Planner 到 Task：计划如何拆，结构语言如何形成

这里有两层 planning：任务级步骤分解，以及当前步骤内的动作选择。

查看规划逐步转换与语义损失

5.1 任务级：TaskSpec → TaskPlan → StepSpec

若 TaskSpec 已有义务图，RulePlanCandidateGenerator 通常按义务生成 StepSpec：每个步骤绑定 objective、InteractionIntent、completion criteria、source refs、depends_on 和 preconditions。随后 TaskPlanAuthorityBinder 才赋予 plan_id、version、based_on_state_version 与 supersedes。模型候选不带这些权威字段。

INTERACTION

InteractionIntent：要怎么与界面交互

有 ElementIntent、CollectionIntent、RelationIntent、RegionIntent 四种类型。例如“结果列表第二项”是 collection + ordinal 关系，不是 CSS selector。

COMPLETION

StateCriterion：什么状态算完成

有 subject、relation、expected、evidence policy 和来源引用。交互方式与完成条件分离，避免“点过按钮”被误算为“效果已经发生”。

5.2 步骤级：PlanningRequest → ActionChoice

PlanningRequestBuilder 从 StateKernel 和当前 BrowserSnapshot 只读投影出不可变请求，绑定 TaskSpec identity/revision、state version、snapshot/page/environment revision、活跃步骤、观测、最近结果、恢复摘要、预算和允许动作种类。任何 identity 不一致或投影过期都会被拒绝。

严格 profile 下，ActionChoiceBuilder 先由 Runtime 根据活跃 StepSpec 和当前统一观测生成合法候选：

  • 0 个候选：返回类型化 grounding/planning 失败；
  • 1 个候选：Runtime 直接选，不浪费模型调用；
  • 多个候选：模型只看到有界列表，只能返回 choice_id；
  • 返回后再次校验 task/state/snapshot/active-step identity 与集合成员关系。
{
  "identity": {"task_revision": 3, "state_version": 18, "snapshot_id": "snap-42"},
  "active_step": {"step_id": "add-to-cart", "interaction": "CollectionIntent(...)"},
  "choices": [
    {"choice_id": "choice-a", "action_kind": "activate", "target_id": "result-2"},
    {"choice_id": "choice-b", "action_kind": "activate", "target_id": "result-3"}
  ]
}
模型输出：{"choice_id": "choice-a"}
“结构化输出”不是只要求模型吐 JSON。真正稳定来自五层组合：有界输入、严格 schema、Runtime 生成候选、返回后身份与成员校验、失败后切换修复 schema。语法正确只是第一层。

5.3 重规划不是把旧计划清零

TaskPlanLifecycle 在动作预算耗尽、动作族不可用、结果已满足或状态不支持时生成 replacement plan；新计划版本必须基于当前 state version，并保留已有验证证据与已完成子目标。计划生命周期本身无状态，持久状态仍由 StateKernel 经 committer 写入。

源码：task_plan_generators.py · planning_request.py · generalist_planner.py

SECTION 06

Agent Loop：每一轮到底怎么走

实现不是简单 ReAct while-loop，而是阶段协议、单写者提交和失败所有者路由。

查看五阶段循环逐步转换与语义损失
Perception捕获一致快照，融合来源；必要时主动探测证据缺口。
Planning对齐当前状态、计划和活跃步骤；选择有界动作。
Action绑定合同，做策略、能力、审批、快照预检并执行。
Progress重新观测，独立验证 effect、step、task 三层进度。
Recovery按失败类型和所有者改变策略；无变化恢复被拒绝。

6.1 一次正常迭代

  1. RuntimeCommitSession.start 创建任务状态与首个 Trace 事件，检查总预算。
  2. PerceptionStage 捕获快照并返回 StageResult；RuntimeCommitter 提交 observation、perception 与事件。
  3. ProgressStage 先做“动作前对账”：页面也许已经满足当前步骤，能验证就直接记进度，避免重复动作。
  4. PlanningStage 生成或更新 TaskPlan，选择当前 ActionChoice，产出 PlannerProposal。
  5. ActionStage 把 proposal 绑定为 ActionContract，立即重观测并预检；审批若需要则进入 waiting_approval。
  6. 执行器返回 ExecutionReceipt；Runtime 记录“发生了什么”，但不宣布成功。
  7. ProgressStage 获取独立后验观测，经 verifier ladder 评估动作效果、当前步骤和整个任务。
  8. RuntimeCommitter 原子提交状态增量与有序事件；终态则生成结果，否则进入下一轮。

6.2 为什么要 StageResult 和 RuntimeTransition

阶段拿到的是分离的 RuntimeStateSnapshot 或只读投影，不能直接写 StateKernel/Trace。它只能返回 output、transition、events、failure、terminal、directive。RuntimeCommitter 是唯一写者，按固定顺序更新状态与因果事件。

单写者（single writer）指只有一个组件能提交权威状态。它降低并发式隐式写入、部分提交和“状态已变但 Trace 没记”的风险，也让架构测试能禁止 Planning/Execution/Progress 模块直接依赖 TraceDag。

6.3 StateKernel 与 TraceDag 的职责

StateKernel：现在是什么状态

保存当前 plan/progress、最新观测、合同、回执、验证、计数器、失败、恢复、排除项、最终结果与 state version。

TraceDag：为什么走到这里

保存父子事件关系、时间、payload 与 artifact refs。当前状态不等于完整历史，完整历史不应反灌进每次模型上下文。

源码：coordinator.py · stage_protocol.py · runtime_committer.py

SECTION 07

从“看到页面”到“执行动作”

目标不是从截图猜坐标，而是把语义意图绑定到当前、可追溯、未过期的界面证据。

查看感知、Grounding 与执行逐步转换

7.1 统一观测

UnifiedObservation 把不同来源投影成 target-centric 视图：每个 target 有 id、surface、role、label、supported actions、state、confidence、conflict codes 和 source refs；整份观测绑定 snapshot、page revision 与 environment revision。

PerceptionSession 负责一次一致捕获，并可保存截图 Artifact。主动感知不是任意探索：EvidenceGap 明确缺什么证据，ProbeCapability 必须只读，ProbeBudget 限制观测、超时、模型调用、成本与产物数，ProbeCommand 要求一个新的、一致的 epoch。

7.2 语义落地 Grounding

Grounding（落地/指代解析）是把“第二个搜索结果”“保存按钮”“图中红色区域”等语义目标，绑定到当前观测里的具体可交互候选。结果显式区分 resolved、ambiguous、absent、capability_missing。候选还携带来源、目标指纹和当前性检查。

StepSpec.interaction→ActiveStepScope→UnifiedObservation→GroundingCandidate→ActionChoice

7.3 ActionContract 的真正作用

PlannerProposal 仍不能直接执行。ContractBuilder 生成版本化 ActionContract，其中包括动作、参数、定位绑定、预期效果、所需能力、风险、审批语义、幂等与补偿信息，并绑定 run、snapshot、page revision、active step 与 verifier criterion。

预检门检查内容防止的问题
Scope / Policy目标是否来自 TaskSpec 授权，是否触发 no_purchase/no_delete/allowed_domains页面诱导与越界副作用
Capability所需 capability 是否由入口授予模型或页面自授权限
Approval高风险操作是否有绑定 run、contract hash、page revision、过期时间的 token审批复用、换页后继续执行
Lease / Snapshot环境、页面、快照、目标指纹是否仍匹配在陈旧坐标或旧 DOM 上操作

预检前会立即重观测；空间目标可在规则允许时 rebound。审批回来后也必须重新观测与重新验证，因为等待期间页面可能变化。审批 token 在 authorize 时原子消费，避免重复使用。

源码：unified_observation.py · active_perception.py · contracts.py

SECTION 08

验证、进度与终态：怎么知道真的完成

执行是尝试改变世界；验证才是判断世界是否改变。

查看验证与终态逐步转换及语义损失

8.1 三层结果必须分开

ACTION EFFECT

动作效果

这次 contract 的 expected effect 是否发生，例如购物车数量增加。

STEP COMPLETE

步骤完成

当前 StepSpec 的全部 StateCriterion 是否被当前证据满足。

TASK COMPLETE

任务完成

TaskSpec 的终端义务与依赖闭包是否成立，禁止效果是否未发生。

ExecutionReceipt 只说明执行器是否分发、报错、超时以及它观察到的底层结果。ProgressStage 会捕获独立 post-observation，运行 verifier ladder，生成 VerificationReport。证据带 verifier kind、target、observed/expected、criterion/requirement IDs、environment、snapshot、强度和语义 key。

8.2 “按钮点成功”为什么仍可能失败

按钮可能吞掉事件、网络请求可能失败、页面可能只显示乐观 UI、目标可能原本就已满足、动作可能作用在错误实体。因而 Runtime 只在后验状态满足来源绑定的 completion criteria 时计入步骤进度。

TerminalReadinessEvaluator 还会检查终端候选的所有前置 obligation 是否 complete、证据是否存在、task revision 和 observation epoch 是否当前、目标指纹是否仍一致。只有 READY 的终端目标才能继续对 Planner 可见。

8.3 活性与防重复

Liveness（活性）表示系统不仅安全，而且能持续产生可证明进展。Runtime 用 RecentActionOutcomeIndex 和 progress fingerprint 识别：

  • 相同页面上效果已经满足，但无法把证据归因给当前步骤：触发 progress-credit invariant；
  • 相同 revision 下同类动作曾验证失败，又准备原样重做：触发 no-progress repeat；
  • 预算是最后安全上限，不是发现死循环的第一手段。
终态权威TaskSpec-backed 任务通常要求独立 passed verification 才能提交 TaskCompleted。最终成功转换和唯一 TaskCompleted 事件由 Runtime 统一提交，Planner 和 executor 都无权宣布终态。

源码：verification.py · terminal_readiness.py · runtime_terminal.py

SECTION 09

失败恢复与安全：不是“一律重试三次”

恢复首先要知道失败发生在哪一层、外部效果是否可能已发生、下一步该由谁负责。

查看失败分类与恢复逐步转换

9.1 统一失败信封

FailureEnvelope 可以覆盖 intake、observation、planning、grounding、preflight、execution、verification、progress、provider context 等阶段，记录 failure class、语义族哈希、精确调试哈希、state/snapshot/proposal/contract 谱系、证据、剩余预算和 effect status。

EffectStatus含义恢复约束
not_dispatched确认未发出可在幂等与预算条件下换策略重试
may_have_occurred超时或验证阶段无法确认先 inspect post-state，不可盲重放
confirmed_occurred效果已确认推进或补偿，不再重复
confirmed_not_occurred确认没发生允许安全重试
irreversible_or_unknown不可逆或未知失败关闭，通常交给用户/终态处理

9.2 失败所有者路由

Owner典型失败动作
runtime_recovery快照陈旧、落地路径失效、需重新观测reobserve / active perception / reground / reroute
step_planner模型 schema 错、候选决策不合法、上下文过大repair schema / compact bounded context / switch provider
task_planner动作族不可用、子目标设计不再适用replacement plan，保留已验证进度
progress效果不确定、证据无法归因inspect post-state / reconciliation
user需要澄清、审批或不可安全推断waiting_clarification / waiting_approval
terminal预算耗尽、不可恢复、策略/能力冲突failed / aborted，保留证据

RecoveryOwnerDispatcher 要求 owner 身份正确、恢复前后 state/dimension 确实变化且有证据；没有改变策略的“恢复”被认定为 no-op。这直接防止重试风暴。

9.3 安全不是一个 Gate

  • 语义层：SourceLedger + TaskSpec 限制用户真正请求的 effect；
  • 范围层：ProposalScopeEvaluator 要求目标文本、序数或关系证据与任务相符；
  • 策略层：read_only、no_purchase、no_delete、no_external_message、allowed_domains；
  • 能力层：CapabilityGate 只承认入口授予集合；
  • 审批层：高风险 token 绑定具体合同与页面版本，并过期、单次消费；
  • 执行层：lease、snapshot 与 target fingerprint 防陈旧操作；
  • 结果层：独立验证与禁止效果检查防假成功。

源码：failure_envelope.py · recovery_protocol.py · safety.py

SECTION 10

上下文工程与压缩：仓库实际做了什么

这是最容易被“通用 Agent 经验”带偏的部分，必须严格按代码表述。

查看上下文投影、压缩与语义损失

10.1 当前实现：每轮重建有界投影

Planner 不直接读取整条 Trace，也不拿完整页面原始数据。PlannerContext/PlanningRequest 按当前 TaskSpec、活跃步骤、当前观测、预算、最近结果、验证状态、恢复摘要和少量 accepted knowledge 重新构建。页面文本、affordance 数、artifact refs 等都有边界；artifact 路径会被哈希化；任务命名还会从某些摘要中移除，降低 benchmark leakage。

StateKernel 当前态+BrowserSnapshot+TaskSpec→只读 bounded projection→model messages

10.2 当前“压缩”具体是什么

compact_planner_context() 会收紧可选展示预算，例如把 max_affordances、artifact refs、accepted knowledge 的上限减半；同时保留 TaskSpec、当前 snapshot、约束、剩余预算、verifier state 等关键控制事实。PlannerContextCompactionOwner 要求产生变化证据。

事实边界当前仓库没有一个通用的 conversation history manager，也没有 Claude Code 式“把长对话压成九段摘要再继续”的完整会话压缩器。把它描述为“实现了通用长对话压缩”是不准确的。

10.3 为什么这种设计仍然能控制上下文

  • 状态外置：StateKernel 保存规范当前态，TraceDag/ArtifactStore 保存完整历史；模型无需携带全轨迹。
  • 语义分层：TaskSpec 与 StepSpec 保存必须无损的目标、约束和完成条件；观测文本属于可裁剪展示。
  • 按需引用：artifact 通过 ref 进入上下文，而非把截图、DOM、所有回执全文反复注入。
  • 恢复有类型：上下文过大只触发 provider-context 所有者的压缩，不与 grounding 或 task replan 混为一谈。

10.4 面向进一步演进的无损/有损分界

必须无损保留

TaskSpec identity/revision、约束与能力、active step、state/snapshot revision、未完成 criteria、审批状态、effect uncertainty、剩余预算、已验证效果引用。

可以有损压缩

重复页面文本、已失效候选、旧截图描述、冗长 provider 错误、已归一化的历史动作细节、可从 artifact/trace 恢复的内容。

如果未来加入滚动摘要，应评估的不只是 token 降幅，还包括恢复正确率、关键事实召回、过期事实残留、端到端延迟和失败后可审计性。这是 Agent Atlas 面试深度带来的检查维度，但不是当前实现声明。

源码：planner_context.py · planning_request_serializer.py · planner_context_recovery.py

11.1 运行时证据

ArtifactStore 按 run 保存 observation、screenshot、receipt、verification、run.json 和 events.jsonl，并为产物计算 SHA-256。TraceDag 的每个节点记录 kind、payload、parents 和 timestamp，写出时成为带 sequence 与 parent_event_ids 的 JSONL。

Trace mining 与 TaskSkill 机制可以从已验证轨迹提取语义模式，但新 skill 先进入 quarantine。只有原任务、任务族、held-out、全局 smoke、安全 smoke 等独立回放证据满足要求，并且报告与 trace/skill payload 做 digest 绑定，才可晋升。这样避免把一次偶然成功直接固化成生产策略。

12.2 设计取舍：为什么不更简单

为什么不用一个大 Prompt 让模型输出完整操作序列？

长序列会在页面变化后迅速陈旧，也把权限、grounding、完成判断混进同一概率输出。当前架构每轮只处理活跃步骤，并用最新观测重建候选，代价是组件与类型更多，收益是可验证与可恢复。

为什么 Runtime 自动选唯一候选，而不是每次都问模型？

唯一合法候选时模型没有增加决策价值，只增加延迟、成本和 schema 失败概率。多候选时才需要模型利用语义偏好消歧。

为什么 StateKernel 不保存完整历史？

权威当前态需要紧凑、一致、可校验；历史则可能无限增长，更适合 append-oriented Trace/ArtifactStore。二者分离也天然限制模型上下文膨胀。

恢复为什么也要“所有者”？

页面陈旧、模型 JSON 错、计划不适用和外部效果不确定不是同一种失败。若都交给同一 retry loop，系统容易原样重试、扩大副作用或掩盖架构责任。
